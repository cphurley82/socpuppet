# Decisions 🧦

Every decision that settled how socpuppet is built, dated, with its reason and where the reasoning lives. Newest first. A decision that reversed an earlier one says so (↔), and the earlier one stays on the page, because the reason it was wrong is the useful part. The decisions still open are in [roadmap.md](../roadmap.md#open-decisions), and the rules that a decision is judged by are in [vision.md](../vision.md).

## 2026-10-22

- **The SSD meets a real host, through pciem, and that is the next milestone**: M30 the spike, M31 the build, both before M29. pciem (Linux, GPLv2) lets a userspace program be a PCIe device on the host's own bus, so this machine's Linux drives the puppet's SSD with its own `nvme` driver. pciem's kernel side plays configuration space, the BARs and the MSI-X table, so it stands where the endpoint, the link, the root complex and the host CPU stand, and the function's three ports (`bar0`, `dma`, `irq`) are the whole interface, unchanged. Asked by the maintainer on 2026-10-22; by *real over toy*, *borrow before building*, and aim 3, *be usable at work*. ↔ Amends the same day's "M29 … is next" ([roadmap.md](../roadmap.md)).
- **pciem's bridge is optional, from source, Linux-only and never in the wheel**, as QBox is: `pciem_api.h` is GPL-2.0-only, and no GPL code goes in the wheel (2026-10-04). 📮 The authors dual-licence their examples MIT/GPLv2; the header is asked for the same.
- **M31's exit test runs on a prepared machine, on demand, and not on GitHub's runners**: pciem needs a physically reserved region on the kernel command line, and so a reboot. A self-hosted runner is an open decision.
- **M30's code is a spike in `spikes/pciem/`**, C++ first, Linux-only, behind the `spike` preset, and the bridge is rebuilt test-first in M31, by 2026-10-16's rule that the spike is only the report.
- **M29 follows M31 and inherits its pump**: the loop that waits on the wall while the CPU sleeps and looks at a file descriptor meanwhile is written once, for `/dev/pciem`'s eventfd first and libslirp's sockets second.
- **`ssh` into Linux is a milestone of its own, M29, on the virtio network card and before M17.** What `ssh` needs is a bridge at the far end of a network card, not a card: 🎭 the virtio card already answers Linux's `ping` under Linux's own driver, so the bridge is written once, as the far end every card shares (`sp.EthernetCable`), and M17's real MAC inherits it. The bridge is user-mode networking, libslirp through ctypes, because a TAP device wants root and *a newcomer builds it for free on a laptop*; the server is dropbear in Alpine's root, its host key made at first boot. ↔ Amends the 2026-10-21 "Real `ssh` ... is for after M17".
- **M24's kernel is still the stock `defconfig`, with NVMe a module, and an initramfs loads it**, as a distro's kernel boots: `firmware/build.py` builds the two modules by name, after the Image (modpost stops when one make has both), and packs `initramfs.cpio` with the kernel's own `usr/gen_init_cpio` (borrow before building): Alpine's busybox and musl, the modules where a distro's kernel keeps them, and `firmware/initramfs/init`, which loads them, waits for the root the command line names and `switch_root`s. Uncompressed, to spare the interpreter the unpacking. Asked of the maintainer on 2026-10-21 against a two-line configuration fragment, by *real over toy*. The fw_jump road places it at `opensbi.INITRD_OFFSET`, 2 MiB past the room the devicetree's copy is given, named in `/chosen`; the UEFI road has UEFI's shell, `uefi_shell.efi` from the EDK2 part, run a `startup.nsh` from the ESP that hands the stub `initrd=`, since RISC-V's stub reads it from its load options and EDK2's RISC-V build has no `initrd` command.
- **The drive keeps its data, so Python programs it as a factory would and reads it back after a shutdown.** The SSD's FTL keeps its table in a reserve at the NAND's start, the fewest whole blocks that hold a header page and an entry for each NAND page; the header is a register map of its own (`regs/ftl_header.rdl`), and the board gives the NAND the room besides the drive (`ftl.nand_blocks`). Both firmwares read the table when they start, and save it when the host shuts the drive down (`CC.SHN`), header last; `socpuppet.ftl` is the layout in Python, and the SSD's contract tests hold the three copies to one another. Asked of the maintainer on 2026-10-21, against Python driving the drive over NVMe from a bus master beside the host's CPU. ⚠️ A drive whose power goes without a shutdown keeps the table it was last shut down with: power loss is M10's.
- **The virtio disk stays the default root**, of `linux.host_with_linux` and `socpuppet linux`; the drive is `root="drive"` and `--root drive`, on M8's board with all three firmwares. Asked of the maintainer on 2026-10-21.
- **Python reads ext4 with `ext4` from PyPI** (Eeems/python-ext4, MIT, pure Python, read-only), in the dev dependencies and the wheel's test requirements: e2fsprogs' `debugfs` is keg-only under Homebrew, so the read-back would have been skipped on the Macs.
- **A controller says what Linux and UEFI read of it**: the namespace's capacity, `NCAP`, which Linux takes for "not allocated" when it is zero, and `CAP.CSS`, the NVM command set, without which EDK2's driver leaves the controller alone. Each is in the NVMe contract.

## 2026-10-21

- **`socpuppet linux` puts your terminal at Linux's console**, a serial console's way, through `socpuppet.interactive.interact`, which any platform can use. While the CPU works the simulation runs flat out; a next moment more than a quantum away is a CPU asleep, and that stretch is waited out on the wall, with a key ending the wait, as QEMU's `-icount sleep=on` does. So `sleep 2` takes two seconds, an idle prompt costs the machine nothing, and the boot is no slower; Linux's clock is ahead of the wall by what the boot gained. Unpaced, the guest's clock raced, a core spun, and Zephyr's shell, with its timer set years ahead, overflowed SystemC's clock. **Ctrl-] leaves**, telnet's and `virsh console`'s key, not QEMU's Ctrl-A, which busybox's line editing takes for Home. **Standard output is the console's bytes and nothing else**, so a pipe can script it, and socpuppet's own lines go to standard error. **What is typed waits for the shell's first prompt**, as a person would: piped input that reached the console during the boot was gone before the shell started. Real `ssh`, through a bridge to the machine's network, is for after M17 (roadmap).
- **CI is two tiers: a quick one on every push and pull request, and everything else every night.** `ci.yml` runs lint, the firmware, the tests but those marked `long` (`test-quick`, `ctest --preset quick`) on `ubuntu-26.04` and `macos-26-intel`, and clang-tidy, coverage and the sanitizers on Linux; `nightly.yml` runs every other job on every machine, `test` on `macos-latest` too, the `on_demand` tests on Linux, and the devcontainer's image on Ubuntu 26.04 and 24.04. Each job of `tools/ci.py` states its tiers, a run here is the nightly tier unless `--quick`, and a job in both workflows is the same text in both but for its machines. A run had taken one to three hours, most of it queued for GitHub's five Macs at a time; the repository is public, so no minutes were billed. Nothing is dropped, only moved to the night and to a developer's machine: *clarity and correctness first, before speed*. The README shows each workflow's badge for main. ↔ Reverses the 2026-10-16 "One CI workflow, with QBox's jobs on every push".
- **The devcontainer's image is built on any Ubuntu, 26.04 unless asked** (`ARG UBUNTU`, `tools/devcontainer.py --ubuntu 24.04`), and the linux preset's tree is each Ubuntu's own, `build/container/ubuntu-<version>/linux`, a folder of the host's on a Mac too, so that `tools/ci.py` there looks after its dependencies. The path-filtered `devcontainer` job became `devcontainer-26-04` and `devcontainer-24-04`, every night and with `--docker` here. ↔ Amends the 2026-10-21 "named for the image's Ubuntu", which left `build/linux` shared.
- **What the container builds for itself is named for the image's Ubuntu**, read from the Dockerfile's `FROM`: on Linux `build/container/ubuntu-26.04/<tree>`, on a Mac the volume `socpuppet-<tree>-ubuntu-26.04`, which `.devcontainer/devcontainer.json` names too. An image of a new Ubuntu starts in fresh trees, where GCC 15 had built on what GCC 13 made against 24.04's libraries; the old ones are left to delete ([development.md](../development.md)). uv's venv and Python are not, since the Python is uv's own and the venv holds only manylinux wheels; nor is `build/linux`, whose dependencies `tools/ci.py` and `firmware/twister.py` look after where it is. ↔ Amends the 2026-10-20 "Docker's container is a machine of its own".
- **The Zephyr SDK, Zephyr and the SDK's LLVM are cached on the runner's system and processor**, not its Ubuntu, since each runs on any Linux of that processor; one copy serves 24.04 and 26.04, and `fetch-sdk` and `fetch-zephyr` run on 26.04 alone. What is built against an Ubuntu's libraries, the fetched dependencies, QBox and ccache, is still cached per Ubuntu.

## 2026-10-20

- **Ubuntu 26.04 is the default**, for CI's runners and the devcontainer's image, where 24.04 was. GitHub's 26.04 runners are generally available, and `ubuntu-latest` moves to them in October and November 2026. 24.04 is still supported, and CI keeps a leg on it where an older Ubuntu differs most: the build and the tests, with GCC 13, and QBox, which links more of the system's libraries than anything else. The jobs that build firmware, check the code, run twister or make the wheels run on 26.04 alone, since what they produce does not depend on the Ubuntu they run on, and the qbox job's leg on 24.04 runs twister there anyway. The wheel's Linux legs, Arm's included, moved from 24.04 to 26.04: the wheels are built in manylinux's container, whose tag is what promises them to 24.04, and the install the way a user would, with uv and with pip, and its boot run on 26.04 only. ↔ Amends M0's "a devcontainer that is the CI environment": it is CI's default one now, beside a leg on 24.04.
- **CI has Intel Macs**, for what an Intel Mac runs natively: the build and tests, QBox and the jobs on it, and the wheels. The firmware and twister, which an Intel Mac builds in the devcontainer's image, are left out, as GitHub's Macs have no Docker. Every other runner was Linux or Apple silicon, so what broke only on an Intel Mac (Homebrew's headers in `/usr/local/include`, the `INTEL_MAC` branches, the tests that run only there) was found on a developer's machine, after a push. `macos-26-intel` runs every one of those jobs; `macos-15-intel`, an older Xcode and SDK, runs only `test`, the quick one. It rests on *a newcomer builds it for free on a laptop*, and an Intel Mac is a laptop people still have.
- **clang-tidy and the header check run on Linux and on a Mac in CI**, and here on every system, reading each machine's own compile commands and standard library: Apple clang's and libc++ on a Mac. One Mac is enough, the newest (`macos-26`): an Intel Mac's compile commands are an Apple silicon one's, its builds already meet Homebrew's `/usr/local`, and `qbox-tidy` on `macos-26-intel` ran for 50 minutes and then lost its runner, most likely to a lack of memory. ↔ Reverses fc752f2, which kept them to Linux because clang-tidy read GCC's: the whole tree is clean on a Mac too, and a Mac's libc++ is not libstdc++, so a header that compiles on one can lack an include on the other.
- **Docker's container is a machine of its own**, with its own compiler and the repository at `/workspace`, so what it builds for itself is kept apart from the host's on every host, not only on a Mac: QBox's two trees, its firmware tools in `build/firmware/linux-<processor>`, and twister's folder. On a Mac each is a Docker volume, as before; on Linux a folder of `build/container`, made first as the caller's, since a named volume is root's and the container runs as the caller ([development.md](../development.md)). ↔ Reverses 9b657b7's "on Linux QBox's trees are the repository's own", which was about speed: the container, with GCC 13 and other paths, built into the host's own trees.
- **A tree that a build compiles this machine's tools into is the machine's**: EDK2's, whose BaseTools are built inside it, joins the kernel's in `build/firmware/<machine>`.
- **On a Mac, socpuppet's build names the SDK** (`cmake/MacSdk.cmake`, before `project()`), the one the compiler would use anyway, unless the build was given one. Apple's clang, when none is named (and CMake 4 names none), finds one by itself but also searches `/usr/local/include`, ahead of every `-isystem` directory, so on an Intel Mac Homebrew's headers stood in for a dependency's own: Homebrew's fmt 12, which came with ccache, broke the adapter's compile against QBox's fmt 9, and `build/dev` compiled against fmt 12.2 while linking 12.0. Named, the SDK is the only system directory clang searches; Apple silicon never met this only because its Homebrew lives in `/opt/homebrew`. QBox's own build is left as it is, since it wants Homebrew's asio from there.

## 2026-10-18

- **M20 meets 🎭 the virtio cast, and only the virtio cast.** Linux's console is the virtio console (`hvc0`) and its root the virtio disk, and every one of the five virtio devices is brought up under Linux's own driver before any hardware model takes a stand-in's place: the 16550 as Linux's console, the drive (M24) and the network card (M17) are each a later step. Asked by the maintainer, so that a kernel meets the small, tested models first and a real block replaces one at a time. ↔ Amends the 2026-10-17 decision's "console on the 16550". `firmware/rootfs/etc/inittab` puts the shell on `hvc0`.
- **The kernel is Linux 6.18, a longterm release** (6.18.57 when pinned), fetched as kernel.org's tarball and checked against the SHA-256 it publishes, built as the stock `defconfig` with the SDK's LLVM: the AIA drivers landed in 6.10, `riscv,isa-extensions` in 6.6, and 6.16 taught the kernel to handle a misaligned access itself; a longterm release takes fixes for years without the pin moving. Settles the roadmap's open decision. A tarball and not a clone, for the size and the checksum, and no patch step, since a stock kernel is the decision.
- **The root filesystem is Alpine's mini root for riscv64** (3.24.2), a stock distribution's root of prebuilt binaries, so no Linux C library cross toolchain is needed, with one inittab of ours laid over it. 🚧 A Debian root is a later item.
- **QEMU's debugger on QBox's hart is made to work in M20**, with no time box: only a fault inside QEMU's own stub, beyond a session, stops it. The maintainer prefers QBox's hart for bring-up, and a debugger whose reads go through the hart's MMU is the one a kernel wants.
- **The shared directory under Linux is a sixth virtio device, the 9P transport, beside the file system device**, serving the same directory by the same tag: `defconfig` builds Linux's 9p client and not virtiofs, and Zephyr and EDK2 have virtiofs and not 9p, so each meets the protocol it has. Slot 5, at `0x1000_6000` on source 23.
- **The 9P2000.L server is our own**, `socpuppet.ninep`, brought to the maintainer with its tests as the vision asks: aio9p is AGPL, which the wheel cannot carry, and speaks 9P2000.u; py9p is of Python 2's era. It answers what Linux's client sends to mount, read, write and create, and `EOPNOTSUPP` to the rest, which the client does without.
- **The server's way is a tier on demand**: UEFI finds the kernel as `EFI/BOOT/BOOTRISCV64.EFI` on a disk with a GUID partition table, and the root in its second partition, the quick way and from the flash. The flash cannot hold a kernel (16 MiB against 26), so the silicon path is ROM, flash, OpenSBI, UEFI, disk. The disk is made at test time from the two images, by `tests/python/gpt_image.py`, so `firmware/build.py` makes no second artifact.
- **"On demand" is a marker**, `@pytest.mark.on_demand(reason)`, which skips unless `SOCPUPPET_ON_DEMAND=1`: an environment variable, because a platform test runs again in a fresh interpreter, which is handed the environment and not pytest's command line. M23's and M28's boots from the ROM keep their parameters, which always run.
- **The instruction trace is QEMU's, through the debugger**, and not a parameter of each CPU as planned: a parameter of ours is a number, so a path would be a binding of its own, and QBox reads QEMU's arguments before anything can hand it one; QEMU's monitor commands do the same through GDB, from wherever the debugger asks. ↔ Planned as `instruction_log=` on both CPUs; the DBT-RISE CPU's trace is a loose end.

## 2026-10-17

- **The first Linux boot takes the virtio road.** A stock `defconfig` kernel on `host(sbi=True, virtio=Virtio())`, its root on the 🎭 virtio disk and its console on the 16550, then the same kernel through UEFI. The initramfs road, with the root filesystem built into the kernel, is the second, the comparison, and the root on the real drive is M24's. The five virtio stand-ins stay on the host, and there is no second, virt-shaped board. By the vision's rules: real over toy (a stock kernel, unpatched), borrow before building (`defconfig` needs nothing of ours for virtio, and has NVMe as a module), and Linux asks, we build. ↔ Supersedes the initramfs-first plan of 2026-10-12; the exit test, a prompt and `uname -a`, is unchanged. [virtio-spike.md](virtio-spike.md), under Decisions and The roads to Linux.
- **The vision is written down**, in [vision.md](../vision.md), and the roadmap is read by it.

## 2026-10-16

- **A spike's models are built in the tree, test-first, and the spike is only the report.** M25 was first written as throw-away code; nothing in `src/`, `python/` or `tests/` may depend on a spike, so stand-ins that M20 would reach for could not live there. ↔ Reverses the plan for M25 as written on 2026-10-12.
- **Five virtio devices, and the shared directory is virtio-fs, not 9p**, because Zephyr and EDK2 both have clients for it. The spike then found that `defconfig` builds 9p and not virtio-fs, so under Linux 9p comes first ([virtio-spike.md](virtio-spike.md), Decisions).
- **The virtio slots are off the host by default** (`host(virtio=Virtio())` adds them); each device has a registry name of its own, because a reader of the address map wants to see "virtio-blk"; the transport's registers are a register map in `regs/`, and the formats a device keeps in memory are written by hand.
- **One CI workflow, with QBox's jobs on every push**, its build cached on its pin and its patches. ↔ Reverses the nightly job of 2026-10-14. Every bash tool became Python with tests, spikes excepted.

## 2026-10-15

- **UEFI is a milestone of its own, before the kernel, though the kernel does not need it.** A kernel finds a fault in the model by hanging, hundreds of millions of instructions in. EDK2 prints every driver's progress, stops at a shell that can be asked questions, and does what Linux does to a hart (paging on from supervisor mode, a timer interrupt there, the whole devicetree read) in a smaller program somebody else wrote. The rehearsal is cheaper than the performance, on the same stage.
- **EDK2, not U-Boot.** Both run on OpenSBI and drive the 16550; U-Boot is the smaller build, but it never turns paging on, which is the thing most worth rehearsing, and a RISC-V server boots EDK2. 🚧 The embedded chain (U-Boot SPL, OpenSBI, U-Boot) is a line for Phase 7 if anyone asks.
- **The kernel's road does not change for UEFI.** M20's exit is `fw_jump` with the kernel where it jumps; UEFI loading the kernel through its EFI stub is a tier of M20 and M24, the way a server does it.
- **EDK2 is `edk2-stable202608`**, QEMU's RISC-V port, built to run at 0x8020_0000 with its variables in RAM, developed on QBox first and tested on both harts. **The boot flash is 16 MiB** (↔ 4 MiB before) with the manager's image in its last 2 MiB; the maintainer chose to grow the IO window to 32 MiB and move the PCIe memory window to 0x1120_0000 to fit it.
- **OpenSBI is v1.9**, built by `firmware/build.py` with the SDK's LLVM and not its GCC: OpenSBI is linked as a position-independent executable, which the SDK's GNU linker, built for bare metal, cannot make. ↔ Planned with GCC.
- **The quick way to boot OpenSBI is QEMU's reset vector in the ROM** (`boot.reset_stub`), not `load_elf`: `fw_jump` wants the devicetree's address in `a1`, and nothing in Python can set a register. Building the devicetree into the firmware (`FW_FDT_PATH`) was turned down because it would make the firmware build depend on the Python description. ↔ Planned as `load_elf`.
- **The root complex is a generic ECAM host to Linux** (`pci-host-ecam-generic`), with no driver of ours, which M24 runs.
- **One APLIC domain, described as supervisor-level and told where to send its messages** (`sp.Aplic(messages_to=)`). OpenSBI writes the message address only into a machine-level domain, and Linux never; QEMU under KVM describes one domain the same way. Two domains with delegation is the faithful step after ([models/aplic.md](../models/aplic.md)).
- **The devicetree's dialect is a parameter** of `platform.devicetree()`, Zephyr's or Linux's, with `mmu-type` and `timebase-frequency` written in both; `host(sbi=True)` and `host(ram=)` with 64 MiB default; `POWER_OFF` on the system controller, because OpenSBI's test payload ends by asking to be switched off; the boot image header gains an argument; `dtc` runs at test time.

## 2026-10-14

- **QBox becomes a milestone, M27: a second hart beside the default, as a second opinion on a boot, never a replacement and never in the wheel.** M26 timed it at nine to twenty times the interpreter and found it could not be held to any of socpuppet's tests from where it stood. Two harts written by different people rarely share a mistake. [speed-spike.md](speed-spike.md), under QBox.
- **One process, one SystemC kernel**: socpuppet moves to QBox's SystemC commit if that is what it takes to link with it; the hart's `time` and `csr` sockets are reached by patching libqemu's export list; and QBox's clock is **128 ns an instruction**, because firmware that waits by spinning ran out of twister's time at 1 ns ([models/qbox-cpu.md](../models/qbox-cpu.md)).

## 2026-10-12

- **The Linux prompt soonest, on a hart and a board already run the way Linux will run them.** M22 to M26 are added: the hart alone with bare-metal programs that do what Linux does, a spike that times it, OpenSBI as a milestone of its own (where machine mode meets supervisor mode and the devicetree is first read by something that is not Zephyr), then the kernel. The IOMMU, Ethernet, the AI processor and the small parts move behind the first prompt, so that each lands under Linux's own driver; shared memory, the NAND that wears, the scenarios and telemetry are Phase 7. 🦜 The Verilator RTL block leaves M11: no block of ours has RTL to put there.
- **The first Linux exit test is a prompt and nothing more.** ↔ It was a prompt, a `ping` and an inference; the `ping` is M17's last line now and the inference M19's.
- **The IOMMU comes after the drive is Linux's root filesystem.** Linux does not need one to boot; the drive's DMA goes untranslated first, as under Zephyr, and M15 puts the IOMMU in its path under Linux's driver.
- 🎭 **Virtio stand-ins are spiked before the kernel, and not planned as blocks.** Asked by the maintainer: a console, a disk and a network that every Linux drives are worth having in hand before the first boot, to hold a real block's place while it is brought up, and to tell a kernel that does not boot from a device that does not work. No real SoC has them, so they stay stand-ins.
- **Every fix to the borrowed CPU is a patch with its entry in [upstream.md](../upstream.md), and every test of the hart is checked with a mutation.**
- **Accessed and dirty bits stay as the borrowed MMU has them** (Svade), and a test pins it; **instruction fetches go through the MMU by a patch**, and the first paging test has the shape of a kernel's mappings; **a patch to a generated file is a patch all the same**, and the real fix belongs in DBT-RISE's CoreDSL description; `ssaia` is listed beside `smcsrind` when the hart's `csr` socket is connected. **The hart has Sv39 and no other kind of paging**, and its ASID reads as zero: nothing here has run Sv48 or Sv57, a kernel is the wrong place to run a five-level walk first, and most chips are Sv39 ([models/dbt-rise-cpu.md](../models/dbt-rise-cpu.md)).

## 2026-10-11

- **Both ways to boot stay, and CI runs both.** Python's loader putting an image straight into RAM is the quick way and the default; `boot=from_rom` is a per-CPU description function, and the CPU then starts in a ROM that finds its image in a flash. **A second APLIC on the compute die** at 0x0C00_0000, for the watchdog's wire. **The boot image header is a register map**, `regs/boot_image.rdl`, so one source describes a file format too. **The watchdog is borrowed** (SiFive's, from VPV-Peripherals) with its behaviour written by us as a patch of some 150 lines, ⚠️ a decision the maintainer may want to look at again. **The system controller is the one driver of every CPU's reset.** Host and manager boot from one flash on the IO die. ↔ A `socpuppet,sources` property and a flash node in the devicetree were planned and dropped: the devicetree already said what they would have. [boot-spike.md](boot-spike.md).
- **Zephyr's own tests run on the puppet under twister**, Zephyr's test runner, with `socpuppet run` as the emulator, a command of the package. The twister files live in the Zephyr module; the board-compliance run is one CI job (a macOS leg joined it on 2026-10-12); it is for CI and before a push, not the inner loop; excluded suites go in a quarantine list with the reason for each. On an Intel Mac it runs from a Docker volume in one invocation, with no ccache. A `FAILED` verdict is a failing exit status, and the cap is exit 0, because twister counts a non-zero exit as a failed configuration (↔ the spike exited 0 whatever the verdict). The SSD board takes a shield, `socpuppet_ssd_host`, with a scripted host in front of it, because a PCIe device does nothing to its host's memory until bus mastering is on. [twister-spike.md](twister-spike.md); [twister.md](../twister.md).

Python pulling the strings, literally; numpy installs everywhere, and torch did not install on the development Mac and is 769 MB. A die of its own stays open: the gate kept it on the compute die for want of a reason to move it. [npu-spike.md](npu-spike.md), under Decisions.
- **Each CPU that asks gets its own GDB server**, by three patches to DBT-RISE, and **a stopped CPU stops the world, and that is the design**: every CPU in one kernel means one clock, so a breakpoint on one holds them all. `sp.Transcript` tells the three consoles as one story, and boot order is asserted only where hardware fixes it. ↔ The other design, a stopped core answering every debugger, is a loose end. [gdb-spike.md](gdb-spike.md).
- **One Zephyr board, `socpuppet_host`, for the host whether or not its dies are split**, because firmware cannot see which die a block is on; the manager is a function handed to `host()`, on a bus of its own; the compute die's window onto the IO die translates (↔ M5's identity window, which the interrupt controller sits in the way of); the timer moves to the compute die; a trace tells direction by where a record was taken.
- **The drive under the host is a function handed to `host()`** (`drive=add_ssd`), the stand-in the default, with board, shield and image unchanged; the quantum is measured and not tuned, and stays 100 µs.
- **The supervisor-interrupt bug in the hart is patched in M13**, time-boxed; 🦜 `sp.MsiPlicBridge` leaves the package and `sp.MsiReceiver` stays; the host's core is `DbtRiseCpu(xlen=64, isa="gc", modes="msu")`. On the way: **the hart reads `time` over a socket pair, not a 64-bit wire** (↔ planned as a wire: a signal cannot carry the CPU's lead, and the timer woke every tick once its count was a signal); `smcsrind` is listed in the devicetree and `smaia` is not, because Zephyr looks for the one; interrupt identities are 0 to 15 the CPU's lines, 16 to 31 the APLIC's sources, 32 and up messages. [aia-spike.md](aia-spike.md).

## 2026-10-09

- **One source for the hardware/software interface.** A register of one of our own blocks is written once, in SystemRDL under `regs/`, and the C header, the Python module and the docs table are generated, checked in and held by lint; offsets had been copied four to eight times a block. SystemRDL because it is the language the industry writes register maps in; writers of our own because PeakRDL's exporters are LGPL or GPL and the wrong shape; only socpuppet's own blocks get a map, since a borrowed model's registers are its project's and a specification's are the specification's. The Python description stays the one place a platform is put together. ↔ Reverses M4's "no shared register header". M14 extended it to a file format, M25 to a transport laid out by a specification, and M15 will bend "only our own blocks" on purpose. [architecture.md](../architecture.md#where-the-hardwaresoftware-interface-is-written-down).
- **The flash controller keeps Zephyr's flash class**, despite three mismatches with raw NAND (a constant write block, offsets limited to 2 GiB, reads at any offset): a learner recognises it and it has a borrowed test, where an interface of our own would be sixty lines with no test and one more thing to learn ([upstream.md](../upstream.md#zephyr)).
- **The die-to-die link is UCIe-style, from public sources only** (the Hot Chips 2023 tutorial and Berkeley's `uciedigital`), never the specification itself, and says it is not compliant. **The mainband is raw memory-mapped TLM**, the endpoint refuses DMI so that every access is seen crossing, and a debugger's look crosses whatever the link's state. One endpoint class, two per link; UCIe's training state machine with a 4 ms reset hold and an 8 ms timeout; a sideband packet is one TLM write; the registers are the Link DVSEC at a static address; the manager releases the compute die by writing 0 to a mailbox. Loosely timed: a latency per crossing plus bytes at a rate, each direction serialized. **No wire crosses the link**: an interrupt or a reset is a sideband message, or stays on its die, which is what led to M13. The manager's stand-in is a Python script, `sp.IoManager`; the CPU kit becomes shared; one Zephyr driver, `socpuppet,ucie-link`, of Zephyr's reset class, because releasing the other die is what that class is for. [models/d2d-link.md](../models/d2d-link.md).

## 2026-10-08

- **Zephyr's stock NVMe driver on the host, with what it lacks supplied by socpuppet's module**, not a driver of our own: borrow first. Mainline cannot deliver MSI on RISC-V and has no polled mode; five workarounds, none a patch ([upstream.md](../upstream.md#zephyr)).
- **The SSD controller is built the way a real one is: hardware for what is the same every time, firmware for what takes judgement.** One RV32 core. The NVMe frontend keeps the queues, fetches each command and posts its completion; firmware reads the command and decides; `CAP.TO` is one second, and one command at a time. Four models (frontend, DMA engine, flash controller, 🎭 ideal NAND), each a plain class with a thin wrapper, and a NAND slot and contract from the start so that M9's realistic NAND passes the same suite. The flash translation layer is a page map and nothing more, and the ideal NAND allows a double program; M9 is where that stops. Two firmware stand-ins, a Python generator and a C++ one for the contract rig, share nothing with the models. Zephyr firmware reaches the hardware through drivers in the module, Zephyr's own flash API tried first. **A fidelity tier is a choice between two description functions in Python**, and the registry gains no mechanism; M6, M7 and M14 carried that up. Nothing takes time in the SSD yet.

## 2026-10-05

- **socpuppet writes its own PCIe endpoint, and VCML stays out of the build.** VCML ends the process on an error, which no test can survive; the adapter around its endpoint was two thirds the size of what it replaced; and its PCI sockets cannot be platform ports, be traced, or cross a link. The modelling-library question is closed: SCC supplies the router and logging, borrowed models sit behind adapters where they fit, and there is no second framework. Reaffirmed for the IOMMU and the APLIC (VCML has both) and for virtio (VCML has them too). [pcie-spike.md](pcie-spike.md), under Decisions.
