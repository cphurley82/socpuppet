# Decisions 🧦

Every decision that settled how socpuppet is built, dated, with its reason and where the reasoning lives. Newest first. A decision that reversed an earlier one says so (↔), and the earlier one stays on the page, because the reason it was wrong is the useful part. The decisions still open are in [roadmap.md](../roadmap.md#open-decisions), and the rules that a decision is judged by are in [vision.md](../vision.md).

## 2026-10-31

- **The first release is Phase 8 and comes before M19; the memory is Phase 9 and comes before the rest of Phases 6 and 7.** socpuppet is useful enough to put in strangers' hands, and the release gate ([vision.md](../vision.md#the-release-gate)) says what that takes: images an installed wheel fetches for itself, QBox in one command, docs read by a stranger, the wheel on PyPI and a container, and then labs of twenty minutes (M32 to M37). The labs come last because the channels a release ships through shape how every lab begins; the gate's first rung, one page and one example, is the docs review's, so the release still passes the gate. The memory comes next because RAM is the largest part of a system still a flat array, and a controller that firmware brings up is what a real boot does first (M38, M39). The rule is aim 3, *be usable at work*, whose bar is a team that installs the wheel and boots; M19 and M17 wait behind both.
- **The firmware images are fetched on first use from a release, not shipped in the wheel.** The wheel stays MIT-only, as [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) promises, and small, under PyPI's cap on a file; the kernel and the Alpine root are GPL and stay stock, with their sources pinned beside them. The cost is a download the first time, and a cache to look after.
- **The channels are PyPI, a Homebrew tap and a container image; Windows is served through WSL.** pip, uv and pipx all read PyPI; the tap is for a Mac user who never touches pip; the container is for a Windows machine with nothing set up, a classroom that wants every seat the same, and the second hart without the build. conda-forge and native Windows wheels wait for somebody to ask: SystemC, Boost and DBT-RISE have never been built with MSVC.
- **QBox's hart stays built from source, in one command from a checkout, and prebuilt only in the container.** GPL stays out of the wheel, but an image offers its sources as a matter of course, so the container is the one channel that can carry it. The contributors' devcontainer stays what it is, a build environment, and is not the published image.
- **The memory milestone is a DRAM controller block, and where the DRAM lives; timing is a tier for later.** By *what a block does matters; how long it takes is a tier*: a controller that firmware brings up before the RAM answers is what the block does, and 🎓 why a chip has SRAM and a boot ROM; latency and bandwidth come when a question asks, borrowed first (SCC's and QBox's memories already carry a latency parameter; DRAMSys for real DRAM timing). A spike comes first (M38), to settle the open decision on the DRAM's die and to look before anything is written, by *borrow before building*. ECC and file-backed contents are loose ends the controller leaves.
- **The roadmap says what and why, never how, and its dependency diagrams are gone.** The table's "Needs" column holds every dependency, so a diagram said it twice and went stale; and how a milestone is built belongs to its planning and its commits, so an undone milestone's section is a few lines of what it delivers and the rule it rests on. By *clarity and correctness first*: a page that said everything twice was read less, not more. The one loose end whose detail lived only there, QBox's hart under the pump, moved to [models/qbox-cpu.md](../models/qbox-cpu.md#what-it-leaves-out).
- **A machine in the docs is its class, never its name, and nobody's name is in them but the licence's.** An Intel Core Ultra 9 285K under Ubuntu 26.04, an Apple silicon MacBook Air, a 2019 Mac Pro: a measurement keeps the machine that made it, since a number without one says nothing, and a nickname says nothing to a stranger, who reads beside an AI assistant that cannot decode it either (the bottom rung's rules, [vision.md](../vision.md#who-it-is-for)). A hostname is a personal detail besides. The speed spike's result files keep every measurement, with the hostnames replaced by the spike's own labels. The same pass took the migration notes and CI's history out of [development.md](../development.md), which keeps what a contributor needs; the history is on this page.

## 2026-10-29

- **clang-tidy 23's new checks are on, with their defaults, and the code was changed to pass them.** LLVM 23 renamed `hicpp-signed-bitwise` to `bugprone-signed-bitwise`, which `bugprone-*` now reaches, and added `readability-trailing-comma`; Dependabot's bump went red with over 1,700 findings. So every literal in a shift or a mask carries `U`, the generator writes a bit as `(1U << 3U)`, a narrow value is widened before it becomes bits, and multi-line lists end with a comma ([style.md](../style.md#c)). The reason is *clarity and correctness first* ([vision.md](../vision.md)): a bit shifted into a signed number's top bit turns it negative, and a negative number sign-extends when it is widened; and a bump of the linter should grow the net, not cut holes in it. `.clang-tidy` now says so and names the families still to come. The trailing-comma fix-it deletes the comma after an empty `{}` of a struct with default members; that is LLVM's bug, worked around in one test ([upstream.md](../upstream.md#clang-tidy)).
- **A pull request lands by auto-merge once the quick tier's CI passed check is green, and main's ruleset requires it, an up-to-date branch, linear history and rebase merges alone.** ↔ "lands by fast-forward" in AGENTS.md: a pull request cannot fast-forward on GitHub, whose rebase and merge writes each commit again, so main's hashes are not the branch's; the history stays linear all the same. GitHub's ruleset names each check it requires, and has no "every check", so CI passed is one job that needs all the others and fails if one failed or was cancelled. It runs `always()`, since a required check that was skipped counts as passed, and not `!cancelled()`, which would skip it in a run cancelled by hand and merge what was never tested. The branch must be up to date with main, so what lands is what CI ran (correctness first, [vision.md](../vision.md#how-choices-get-made)); the cost is a second run when two pull requests wait. The repository's admin may bypass the ruleset. Borrow before building found a ready-made action for the same, re-actors/alls-green, not worth a dependency for two lines.
- **The quick tier's Mac is Apple silicon, `macos-latest`; the Intel Macs run only at night.** ↔ 2026-10-21's two tiers, which put `test-quick` on `macos-26-intel`, and 2026-10-28's three test tiers, whose Intel Mac quick leg left the boots out. The Intel Mac was the slowest leg of every run (27 minutes against Linux's 20 in run 40903346703, which it also lost, to a platform test stopped while its process was still starting) and the one most often broken by what only it has. On Apple silicon the nightly `test` job, every boot, takes 42 minutes against `macos-26-intel`'s 75, so the quick preset runs there whole, boots included. 2026-10-20's Intel Macs stay in `nightly.yml`, `macos-26-intel` and `macos-15-intel`, and an Intel Mac's own `tools/ci.py --quick` still leaves the boots out.
- **What a build keeps for the next run is saved by main's runs alone, and the quick tier's builds compile through ccache.** The repository's caches stood at 10.9 GB, over GitHub's 10 GB: 8 GB of it the fetched dependencies, and 4.8 GB copies that pull requests had saved for themselves. Those caches also held what the dependencies were built into, which a run built again anyway, its build tree being new: 593 of the coverage job's 700 compiles, 7 minutes. So the setup action saves the fetched dependencies, without their builds, only on main, and test-quick, qbox-quick, coverage and the sanitizers compile through a ccache for each set of flags, saved on main for each set of dependencies and renewed weekly, as the wheel job's already was for each set. No machine was dropped to make the room. The nightly-only builds go without: nobody waits for them, and their caches would cost a quarter of a gigabyte a machine.
- **A job of both tiers is written once, and every job's setup is one action.** ↔ 2026-10-21's two tiers, whose shared jobs were copies, held word for word the same by a test. The jobs both tiers run are in workflows both call, `firmware.yml`, `checks.yml` and `qbox-build.yml`, each handed the machines its tier runs it on, and every job takes uv, the system's packages, its caches and its artifacts from `.github/actions/setup`, which held nineteen copies of the apt step before. The cost is that a job needing any part of the firmware waits for all of it, which only twister and the real host's guest did not before; at night that is minutes. The packages stay sets in the action, not the doctor's lists: QBox's on CI are the devcontainer image's, far more than `tools/build_qbox.py` checks for, and making the two agree is its own change.

## 2026-10-28

- **A class of Linux tests boots once, and the Python tests are handed out a test at a time.** `@pytest.mark.platform(scope="class")` runs the tests of a class that the session selected, with the same parameters, in one process, so a class-scoped fixture boots the board once for all of them; the classes whose tests each read the same booted Linux or OpenSBI use it, and about 60 boots became about 25. The plugin makes an xdist group of each such class and the suite runs `--dist loadgroup`: `loadscope` had kept every class on one worker, so a class whose tests each boot booted them one after another, and that, more than the count of boots, set the nightly run's pace. The `dev` preset went from 5 min 13 s to 3 min 22 s here, and the CPU time spent from 59 to 51 minutes; the `qbox` preset runs in 74 s. A class whose tests each build their own board, or switch it off, keeps a process a test.
- **↔ `on_demand` is gone, and its tests are `long`, every night with the other boots.** It reverses the decision of 2026-10-18 that put Linux through UEFI behind `SOCPUPPET_ON_DEMAND`: with the tiers, every boot but one for each area already waits for the night, so a third kind of test, with a job and a variable of its own, kept nothing out of a push that the tiers do not. The plugin's marker went with it (🦜 in [architecture.md](../architecture.md)).
- **The tests come in three tiers, a test preset each: `fast`, `quick` and `dev`.** The full suite took five minutes, almost all of it some 35 boots of Linux and UEFI on the interpreter, so every push and every step of a change waited on them. `fast` is the C++ tests and the Python tests not marked `long`, about 25 s; `quick` adds lint, the tooling tests, the short examples and one boot for each area (the `representative(area)` marker), about 100 s, and every push runs it on both harts on Linux (`qbox-quick` beside it, where a boot of Linux takes seconds); `dev` is everything, nightly. The one `pytest` ctest entry became three, `pytest`, `pytest_boots` and `pytest_long`, each with a label for the presets to choose by, and `SOCPUPPET_SKIP_LONG` went: `-m` chooses. The Intel Mac's quick leg leaves the boots out and keeps the build and the rest. Nothing was dropped, only moved to the night, and the interpreter still boots one test of each area on every push, since it is what the wheel ships ([vision.md](../vision.md): clarity and correctness first, before speed). On the way, the tooling tests went from 225 s to 25 s by being handed out a test at a time (`--dist load`): `--dist loadscope` had kept the 45 runs of one test of `tools/ci.py` on one worker.
- **Milestone names live only in the roadmap and the history.** A test, an example, a comment or a page says what a thing does, not which milestone built it: `test_m20_exit.py` is `test_linux_boots.py`, `examples/m0_passthrough.py` is `examples/passthrough_hello.py`, and "M8's board" is the full bootchain's board. A milestone number tells a reader when, which they rarely need, and not what, which they always do, and the personality's rule is to call a thing by that one name everywhere ([AGENTS.md](../../AGENTS.md), 🎓 Teach as you go). The roadmap still names the test that proves each milestone, and nothing outside it points back, so its tracking can be pruned without touching the code.
- **M18 is done: the small essentials, under Zephyr's own samples and tests and Linux's own drivers.** The boot flash is SiFive's SPI controller with a W25Q chip of ours; Zephyr's `spi_flash` sample and `spi_loopback` test pass, the second against 🧵 Python's loopback, and Linux reads and writes it through `spi-nor` as `/dev/mtd0`. The GPIO passes Zephyr's `gpio_basic_api` with Python's wire between two pins, `blinky` blinks its LED, and Linux takes it with its four lines. The I2C controller passes Zephyr's `i2c_ram` against Python's RAM, its RTIO cases too. The real-time clock passes Zephyr's `rtc_api` with a driver of ours, and Linux sets its clock from it (`test_m18_exit.py`, `test_linux_boot_flash.py`, `test_linux_gpio.py`, `test_linux_rtc.py`). M19 is next.
- **A GPIO's far end is told of a change from the GPIO's own thread, a delta cycle on, and not inside the CPU's write.** The plan had Python called synchronously, so that Zephyr's `gpio_basic_api`, which reads an input straight after writing the output wired to it, would see the wire's answer at once. But a QBox CPU writes from a QEMU coroutine that must not wait, and Python is reached only by waiting for the executor, so the SPI controller's rule holds here too: a device is called from a process of its own. The shield `socpuppet_host_gpio_loopback` sets the test's own `READ_DELAY`, a millisecond, for wiring that is slow ([models/gpio.md](../models/gpio.md)).
- **A GPIO's wires are described with it, and every listener is told.** `sp.Gpio(wires={0: 1})` is installed as the platform is built, as the flash's SPI devices are, because `socpuppet run` builds the board for a shield and has no moment after; and a second listener no longer takes the first's place, so a wire and a script watching the pins live together.
- **Zephyr's SiFive GPIO driver finds pin n's interrupt as the node's interrupt n.** The patch to it hands each pin's handler its pin, where it asked a PLIC, and drops the arithmetic on interrupt numbers of two levels; so a board's pins need not have their lines at sources one after another, though the host's do. 📮 It is one to send ([upstream.md](../upstream.md#zephyr)).
- **Linux's tree has the GPIO, and not its LEDs.** The node is also an interrupt controller there, as Linux's binding asks; the stock kernel has no LED drivers (`NEW_LEDS` is not set), so `gpio-leds` would bind nothing. Driving a pin under Linux waits for a tool busybox has not.
- **The I2C controller is a command device of ours, with the OpenCores core's map, and its devices are Python's.** `CommandDevice` gains the time a command takes, nine of the bus's clocks for a byte, asked as its thread wakes and zero for a write that is no command. Linux's tree has none: `i2c-ocores` is not in the stock kernel, and a config fragment stays the maintainer's call (2026-10-21). Zephyr's `i2c_sifive` sent a device's address unshifted and started every message again, and two patches put it right, both to send.
- **The real-time clock is the Goldfish one, ours, and keeps the simulation's time.** Linux's `rtc-goldfish` is in the stock kernel and Zephyr has no driver for any clock QEMU's `virt` has, so socpuppet's module has one, which sets and gets the time and does not offer the alarm. Its time is what Python gives it, 1970 if nothing, and goes on with the simulated time, not the wall's: a run is the same each time.
- **A milestone's Linux half is a boot module of its own** (`test_linux_boot_flash.py`, `test_linux_gpio.py`, `test_linux_rtc.py`), because long tests are handed out in the order they are collected and a module in `BOOTS` must be boots alone.
- **The root of Linux's devicetree says `compatible = "socpuppet,platform"`.** 🐧 Linux 6.18 takes a root with no `compatible` for the empty tree it builds in, and then refuses the dummy power supply a device whose node names none would otherwise get: `spi-nor` asks for one, so the flash went unprobed with no error but a warning. Any platform socpuppet describes says it, as QEMU's `virt` says `riscv-virtio`, because the generator does not know which board it is describing; the board's name is `model`. Zephyr's trees are unchanged, since nothing of Zephyr's reads it.

## 2026-10-27

- **Only a bus master that can reach the boot flash's controller is told of the flash, and on the 32-bit boards none can.** The SSD's and the manager's CPU kits map the flash's window and not its controller's registers: their boot ROMs read the window, and no firmware of theirs speaks SPI to the flash, where a node would have brought Zephyr's SPI NOR driver into every image built with the flash API, the SSD's among them, and Zephyr's flash test would have tested the boot flash instead of the NAND. The host's flash, which Linux and Zephyr are to drive, keeps its registers at `0x100D_0000` and has its node, in Zephyr's dialect: the controller's, the chip inside it, and a fixed clock of 50 MHz, which socpuppet's `soc.h` gives SiFive's drivers as `SIFIVE_PERIPHERAL_CLOCK_FREQUENCY`. Linux's node followed once the controller's interrupt was wired, which Linux's driver requires: the same controller and chip without the properties only Zephyr's bindings have, and Linux reads the chip's id from the chip.
- **M18 comes before M19, and is four blocks, not five: 🎭 the virtio entropy device is the TRNG.** It is seeded from Python, Zephyr's entropy test runs on it, and since M20 Linux's own driver reads it as `/dev/hwrng`, the seeded stream, which is everything the roadmap's TRNG was to do; a block of our own would have added only a real block's register shape, and a driver for it in each operating system. By *Linux asks, we build*, as M17 was deferred. Asked of the maintainer, who asked whether a second generator was needed at all. 💡 The one-register generator the roadmap had in mind is read by Linux's `timeriomem_rng`, which the stock `defconfig` leaves out.
- **The boot flash's controller becomes VPV-Peripherals' SiFive SPI, and the flash chip becomes ours.** The borrowed chip, `generic/spi_mem`, speaks SCC's SPI packets, which carry no chip select, so a read of any length cannot be framed, and it is behind `minres/qspi`, which no operating system drives. The SiFive SPI is what Zephyr's `spi_sifive` and Linux's `spi-sifive` drive, and it hands its device one byte at a time; joining the two would mean adding chip select to SCC's protocol, a change of protocol and not a fix to a model. So `minres/qspi` and `generic/spi_mem` leave the build, and a JEDEC NOR flash of ours, plain C++ written against QEMU's `m25p80` as the reference (read for its behaviour, copied from not at all, since it is GPL), takes the chip's place under Zephyr's `spi_nor` and Linux's `spi-nor`, unchanged. The window a boot ROM reads through stays. Asked of the maintainer, against a patch to `spi_mem` with a bridge, and against leaving the flash alone.
- **M18's blocks are all on the host's IO die, at the pages after the IOMMU, and Zephyr's SiFive GPIO driver is patched for a board with no PLIC.** Its interrupt handler asks the PLIC which line it was, and the host's interrupts arrive through an APLIC and an IMSIC; the patch gives each pin's handler its pin, and is one to send upstream. The GPIO's four pins take the IO die's APLIC sources 25 to 28, the SPI 29, the I2C 30 and the RTC 31, which is the last of the sources wires have. Asked of the maintainer, against putting the GPIO on a board with a PLIC as well.
- **M15 is done: the drive behind an IOMMU**, the RISC-V IOMMU specification's, under Zephyr and Linux ([models/iommu.md](../models/iommu.md)). Zephyr's disk test passes with the drive let through untranslated and through page tables its driver set up, with the stand-in drive and with the SSD, and the page tables are walked across the link before the drive's first access; the driver's own test takes a page away from the drive and reads the fault record, with the drive's ID and the page's address. Then Linux 6.18's `riscv-iommu` brings it up on its wire, and the root on the drive is mounted through a context Linux programmed, with no fault (`test_m15_exit.py`). M19 is next.
- **The IOMMU is socpuppet's own, written in MINRES's style for VPV-Peripherals' `rvi/`**, in `src/vpvper/`, a tree laid out as VPV's so each file has the path it would have there, behind an adapter of ours as a borrowed model is, by *borrow, and give back* (aim 4) with nothing to borrow: VCML's is ruled out by its `abort()` on error, and QEMU's is not SystemC. Its register map is `iommu.rdl` in VPV's dialect, and `gen/iommu_regs.h` is written by hand in the shape MINRES's generator makes, held to the map by `tests/tooling/test_vpvper_registers.py`; clang-tidy holds it to bug checks alone, and cpplint leaves it be. ↔ Settles the roadmap's "a register map in that project's style".
- **The IOMMU translates a transaction a page at a time**, each page where its own entry says, and a page that is refused stops the transaction there, with the pages before it done and the fault record for that page: what a real IOMMU does, since the fabric hands it a PCIe request of at most 4 KiB. ↔ The first model translated the first byte's address and sent the transaction on whole, which no device in the tree could show, as both drives cut at the host's page: a device that did not would have landed the rest of a transfer at whatever follows the first page. Refusing the whole transfer was the other road, and is not what hardware does.
- **The walk is a plain class, `iommu_walker.h`, unit-tested on its own**; decoding a command and laying a fault record out are the model's, tested through the contract, since nothing else uses them. ↔ Amends the plan, which had all three in the walker.
- **A device ID crosses as a TLM extension of the model's own**, `iommu_device_id`, which socpuppet's adapter sets from the PCIe requester ID; the upstream model knows nothing of PCIe. An access that says nothing is refused with no record, since a record names a device. **The device-ID parameter for a master with no PCIe waits for M19**, the first such master.
- **The endpoint takes all sixteen bits of its requester ID from the configuration writes to it**, where a real function takes only its bus and device numbers: it is a single function, and the root complex reaches it as function 0 alone.
- **On the host, the IOMMU is at `0x100E_0000`, its line at the IO die's APLIC's source 24**, between the root complex's `dma` and the link: so the drive's interrupt messages are translated too, and a device's page tables have to map the IMSIC's page. Opt-in, with `host(iommu=True)`. ↔ Amends the plan's `0x100D_0000`, where the boot flash's controller already was.
- **Zephyr's driver is socpuppet's** (`drivers/iommu/riscv_iommu.c`), since Zephyr has no IOMMU subsystem: a directory of one level, page tables from a pool, a command queue it polls so that it works before the kernel is up, and a fault queue on the wire. The root complex's driver attaches each requester ID its node's `iommus` lists before it scans the link, untranslated by default or through page tables that map the RAM and each IMSIC's page to themselves (`CONFIG_SOCPUPPET_RISCV_IOMMU_IDENTITY_PAGE_TABLE`).
- **M17 is deferred, and M15, the IOMMU, is next.** Linux does not ask for a second network card: 🎭 the virtio card already answers `ping` and carries `ssh` under Linux's own driver, and the roadmap's MAC, VPV-Peripherals' `minres/ethmac`, has no driver in Zephyr or Linux, so both would be ours. Linux does ask for an IOMMU: its `riscv,iommu` driver is in the stock kernel. By aim 6 and *Linux asks, we build*, which ranks above *borrow before building*, and by *real over toy* ([vision.md](../vision.md)). Decided by the maintainer while M17 was being planned. The three roads for M17 (VPV's MAC with drivers of ours, LiteX's LiteEth under both operating systems' own drivers, a PCIe card after a spike) are an open decision in [roadmap.md](../roadmap.md#open-decisions). ↔ Amends the 2026-10-22 order, which put M17 after M29.
- **M15's Linux line is a device context with no page table**: in Linux 6.18 the DMA API's IOMMU layer is not built for RISC-V (`CONFIG_IOMMU_DMA` is `def_bool ARM64 || X86 || S390`), so every device gets an identity domain, and Linux's driver puts the drive behind a Bare first stage. The translating and faulting lines of M15's exit are Zephyr's. ↔ Amends M15's exit in the roadmap.

## 2026-10-24

- **M29 is done: `ssh` from this machine reaches the simulated Linux**, over 🔌 `sp.EthernetCable` ([models/ethernet-cable.md](../models/ethernet-cable.md)): Linux takes an address by DHCP, dropbear answers, and this machine's `ssh` runs `uname -a` there and its `scp` sends 256 KiB that `sha256sum` at the console reads back, on the interpreter (4 min) and on QBox's hart (45 s) (`test_m29_exit.py`). `socpuppet linux` plugs a cable in, with ssh at port 2222 ([linux.md](../linux.md#over-ssh)). M17 is next.
- **The cable is libslirp, through ctypes glue of ours, held to a contract suite**, as the roadmap had it: QEMU's user-mode network needs no root, by *a newcomer builds it for free on a laptop*, and has no Python binding. The configuration is version 1, which every distribution's libslirp has, with IPv6 off, so slirp makes no timer of its own and reports no error of the guest's, and those callbacks are NULL. slirp's clock is the wall's, since its sockets are this machine's and the pump waits on the wall.
- **The cable is a far end like any other, and the pump learns a deadline**: `PumpedFarEnd.due_in()`, the seconds until a far end has something to do that no descriptor says, which for the cable is slirp's TCP timers. One descriptor stands for all of slirp's sockets, a selector's, as `/dev/pciem`'s eventfd stands for the drive's host.
- **Root has no password, and dropbear lets it in (`-B`)**, rather than a key pair made at build time with its public half in root's `authorized_keys`. Nothing private is built into the image or the wheel, no `ssh-keygen` is needed, nor a `chown` of `/root` at each boot (an image made unprivileged carries the builder's uid, which dropbear refuses on `authorized_keys`), and `ssh -p 2222 root@localhost` works for anyone, as the console does. Only this machine can try, since the cable forwards from 127.0.0.1 alone; ⚠️ any user of this machine can be root on the simulated Linux while it runs, which linux.md says. By *clarity and correctness first* and the first rung. ↔ Amends the roadmap's key pair for M29.
- **dropbear and OpenSSH's SFTP server come from Alpine's packages, each pinned**, beside the mini root in `firmware/versions.toml`, with the two libraries dropbear needs that the mini root has not. OpenSSH's `scp` speaks SFTP, which Alpine's dropbear runs from `/usr/lib/ssh/sftp-server`, so plain `scp` works. Alpine publishes no SHA-256 of a package and keeps only its newest build, so each pin's checksum is the file's as fetched, and a stale pin says to pin the newest ([upstream.md](../upstream.md#alpine)). The root filesystem is laid out afresh for each build, no longer in the cached tree.
- **udhcpc asks for an address before the shell starts**, twice a second apart, then in the background: it clears the card's addresses as it starts, and on a slow CPU took the one M20's ping test typed at the shell. ↔ Amends the plan's `::once:` line.
- **M29's exit test boots as fast as the simulation goes and plugs the cable in at the prompt**: a boot that is pumped keeps to the wall's clock while the CPU sleeps, which on QBox's hart made 8 minutes of a boot that takes seconds. A cable plugged in late hands slirp only what comes after.
