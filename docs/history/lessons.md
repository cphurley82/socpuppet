# Lessons 🧦

What building socpuppet taught, by topic: the gotchas a contributor wants to know before touching that area, and the findings that will matter again. Where another page already holds the detail, the line here is short and points at it. [upstream.md](../upstream.md) has every patch and workaround with how to see the fault; the spike reports in this folder have the measurements; the model pages under [models/](../models/) say what each block leaves out.

## Borrowed models and their contracts

- **A borrowed model is trusted as far as it has been run.** The CPU had run Zephyr in machine mode and nothing else, and all fifteen faults M22 found were in what Zephyr never does: paging, user mode, the supervisor's registers, floating-point state. Any of four would have stopped Linux at its first instruction, its first SBI call or its first lock across an interrupt. Run a borrowed block the way the next firmware will before that firmware is on it.
- **A contract suite written first finds real bugs in every borrowed model it is pointed at**, and did: four patches of 99 lines for three VPV peripherals, with no model given up ([architecture.md](../architecture.md#borrowed-models)).
- **A borrowed block that is all registers and no behaviour is a patch, not a model of ours.** Write the contract first, then the patch, and mutate the patch until every line fails a test. A patch drafted before its contract "passed whole the first time" and was wanting in three ways: the test review, the design review and the mutation each found what the others could not.
- **Read the borrowed code first, then write the test that is red for the reason you read.** The reviews that read it again found the same fault in a sibling core, a mask hiding a field, and a reservation that was a map.
- **Run a borrowed driver on both harts before trusting it.** QEMU's hart does misaligned stores in hardware and hid Zephyr's misaligned virtqueue table; the interpreter traps on it, as the specification allows ([upstream.md](../upstream.md#zephyr)).
- **Zephyr's AIA drivers and its virtio drivers had never run on any board in its tree.** A first-time run is where the glue is found, and the module is where it goes.
- VPV's timer and PLIC registers are indeterminate until reset is pulsed, so every adapter around a VPV model resets it at start. VCML is ruled out by its `abort()` on error, however complete its IOMMU and APLIC are; they are good to read beside the specifications. The flash controller keeps Zephyr's flash class although it is a loose fit for raw NAND ([decisions.md](decisions.md), 2026-10-09). The watchdog's behaviour is a 150-line patch of ours to a borrowed shell, which the maintainer may want to look at again.
- **Patches stack.** The patches of one project are applied in the order `cmake/Dependencies.cmake` lists them, so a new one is a diff against what the earlier ones left; `git apply` never applies a patch twice, and a second build tree keeps a stale copy until it is deleted ([development.md](../development.md#dependencies)). A patch to a generated file is a patch all the same; the fix belongs in DBT-RISE's CoreDSL description.

## The hart

- The fifteen M22 patches and the earlier ones (a supervisor's interrupt that could never be taken; a pending interrupt that dropped the instruction it arrived at; `mip` bits firmware could clear; a reset shorter than a busy core's lead; a handler re-entered for the rest of the quantum) are each an entry in [upstream.md](../upstream.md#dbt-rise-riscv), and [models/dbt-rise-cpu.md](../models/dbt-rise-cpu.md) says what the hart leaves out.
- **The dropped-instruction bug was found by diffing 1.3 million instructions of trace** from both cores for the first divergence. Instruction tracing on two harts is the tool when firmware works on one and not the other.
- **The hart sees every fetch, and the interpreter cannot see `mstatus`**, so the fixes for floating-point state and misaligned atomics hang on that, and a translating backend, which fetches another way and has its own copy of every instruction, has none of them ([speed-spike.md](speed-spike.md), The backends).
- **A CSR nobody answers is an illegal instruction.** The adapter registers its CSRs in `end_of_elaboration`, because `register_csr_rd` works only once the core exists; and a claim through `mtopei` needs the same two-delta yield a bus access has, or the handler runs 136 times a quantum ([models/imsic.md](../models/imsic.md)).
- **What a reset leaves behind**: `satp`, the TLB and a reservation stay as they were, and OpenSBI writes `satp` first. Reading `satp` does not empty the TLB; Linux does it. A kernel drops a reservation with `sc` on the way out of every trap, which is why a map of reservations broke it.
- **OpenSBI finds out what the hart has by trying each CSR under its own trap handler**, calls this one privileged spec 1.10 for want of `mcountinhibit`, and detects Smaia by reading `mtopi`, so the hart needed one. It writes `mcounteren` all ones and Linux gives programs `time` only, so `rdcycle` traps in user space here as it does on a chip. Who catches a misaligned access: OpenSBI, from `mepc` and `mtval` with `MPRV` set, through the kernel's page tables; Linux 6.16 and later asks to do it itself.
- `rv64gc_msu` has no PMP: DBT-RISE builds supervisor mode or PMP, not both, and `CONFIG_USERSPACE` wants the `_mu` hart, which is a loose end. DBT-RISE's core names are irregular, so socpuppet offers the few it uses and refuses the rest by name.
- **A CPU with nothing loaded is slow and loud**: a warning per fetch, a hundred thousand lines, a 25 MB report. Give a bystander CPU `hello_world`.

## QBox, the second hart

- [models/qbox-cpu.md](../models/qbox-cpu.md) has what it does differently and its table of fates; [upstream.md](../upstream.md#qbox) has the patches: one SystemC kernel and SystemC's commit pinned to QBox's, `wfi` suspending the kernel, `rdtime` and the AIA registers reached by two exported hooks, a reset handler that has to run from a thread, Sstc switched off or QEMU divides by zero timing it.
- **QEMU's clock is an instruction count.** A target's delay inside the quantum is forgotten, so a boot on QBox tells order and not how long a device makes things, and with no quantum QBox never waits for SystemC's clock. 128 ns an instruction was chosen because firmware that spins ran out of twister's time at 1 ns; it also made the Python suite three times faster.
- **QBox looks hung when it is only slow**: a quarter later in CPU time than the interpreter on UEFI. Time a boot on both before calling a stop a hang.
- **QEMU's debugger works under QBox, with two things to know.** QEMU's `-S`, its own way to hold a CPU for a debugger, leaves QEMU's CPU loop waiting on a thread's condition variable before the machine starts, and as a coroutine that thread is SystemC's: the kernel is stuck, and a debugger's read of memory, which QBox serves on that thread, never returns. Hold the CPU over QBox's halt line from a method in the first delta cycle instead, which the started loop answers by yielding, and keep a channel attached as suspending meanwhile, or a kernel with nothing scheduled moves time to the end of the run before the debugger has said a word. And QBox judges a debug access by a response status that a debug transport need not set, so the adapter sets it when every byte moved ([upstream.md](../upstream.md#qbox)). A stack trace of the hung process (`gdb -batch -ex run -ex "thread apply all bt"` with an alarm in the script) found both in an hour that reading had not in two.
- QEMU's translations are keyed by physical address and dropped at every `sfence.vma`, so it is slower than LLVM on a loop that fences; threaded QEMU crashed everywhere and is not repeatable ([speed-spike.md](speed-spike.md), QBox).

## Time, the quantum and sleeping CPUs

- **A CPU sees an interrupt up to one quantum late.** That is temporal decoupling doing what it says ([architecture.md](../architecture.md#words-you-will-meet)), and a test that times one allows for it: a console's times are good to a quantum each, so a test that subtracts three of them needs three quanta of room.
- **The quantum is one number a process**, SystemC's global quantum set at `build()`; "a quantum for each CPU" cannot mean anything. Measured on M6's two CPUs: 100 µs is thirty times faster than 0 and stretches the run three percent; 10 µs costs a quarter more wall time; 1 ms buys nothing and stretches 29 percent. What a longer quantum stretches is the host alone, and where it goes was not chased. The interpreter's rate on a counted loop does not change with it.
- **Python cannot see 20 ns in `platform.time`.** Measure through the trace, or set the quantum to 0. DBT-RISE counts a target's delay in whole 100 ns cycles minus one, so a crossing under 200 ns costs the CPU nothing ([upstream.md](../upstream.md#dbt-rise-core)).
- **Time is a socket, not a wire.** The hart reads `time` over a socket pair with its lead as the delay: a signal cannot carry the lead, and the timer woke every tick once its count was bound to one. The borrowed timer charged a writer ahead of the clock for its lead a second time, and a 32-bit Zephyr writes `mtimecmp` in three halves, so it lost three ticks a wait ([upstream.md](../upstream.md#vpv-peripherals)).
- **A CPU goes to sleep without letting the clock catch up**, and `wfi` sleeps only while nothing enabled is pending. The watchdog goes by the simulation's clock, the machine timer counts the CPU's lead in. `sc_time` ends at about 213 days; Zephyr's idle thread arms `mtimecmp` 186 days ahead, so the timer contract covers a compare too far off to come.
- **A DMA and an interrupt message take no simulated time**, and the first host memory with a latency is where to honour one. On the SSD only the firmware takes time, one to two milliseconds a command, and the drivers poll `BUSY` with a give-up that only works while nothing else does. A device working for the SSD's CPU does its work in the delta after the write, in undefined order with the CPU: firmware polls or takes the interrupt, and so does a test. A status register can read "up" a delta before the wire driven from it rises; `LineWatcher::WaitForLevel` is for that.
- **`Platform.run_until` looked a moment early from M0 to M8**: asking the kernel what came next let a moment's activity happen, and asking it to run for no time when the deadline was now drew a warning on stdout. Simulated time does not move while a debugger holds a CPU, so a test with a debugger says continue in a `finally`.
- **A hang is expensive**: two minutes of wall time for two seconds simulated on two CPUs. Give a test a tight simulated limit; the pytest plugin's cap is 300 s. Start-up grows with the drive: half a microsecond a page for the flash translation table, so a 2 GiB drive adds a quarter of a second, and the host is not ready for any drive until 0.12 s.

## Interrupts

- **One number is an interrupt all the way.** Zephyr's IMSIC driver takes an identity as the flat IRQ number, so 0 to 15 are the CPU's lines, 16 to 31 the APLIC's sources sent as their own number, and 32 and up messages; 63 identities keeps clear of Zephyr's `eie` bug above 63 ([models/imsic.md](../models/imsic.md); [upstream.md](../upstream.md#zephyr)).
- **The glue Zephyr needs** is in the module and each piece is an upstream entry: `arch_irq_enable` wrapped with the linker's `--wrap`, since a module cannot redefine it and nothing in Zephyr sets an APLIC source up; the APLIC driver never sets `domaincfg.DM` and sets a reserved bit, so the model is held in MSI mode whatever is written; Kconfig cannot see `interrupts-extended`, so a node whose driver asks whether it can interrupt needs `short_interrupts`.
- **A level that stays high after one handler**: an APLIC in MSI mode sends once on the rise. Linux writes `setipnum_le` after each handler; Zephyr does not, so the module wraps each handler to do it. The alternative, Zephyr's `CONFIG_UART_NS16550_WA_ISR_REENABLE_INTERRUPT`, covers the UART only; the maintainer may want to revisit.
- **A shell that polls passes every test but the one that counts interrupts.** The 16550 polled for a whole milestone and nobody noticed until a test looked for the message. When firmware is meant to be interrupted, assert the message or the line, not only the answer.
- **One APLIC domain described as supervisor-level works for OpenSBI and Linux, but nobody then writes where its messages go**: OpenSBI only for a machine-level domain, Linux never ([models/aplic.md](../models/aplic.md)). OpenSBI refuses an IMSIC whose `riscv,group-index-shift` is below 24, and the refusal fails its whole irqchip scan. The supervisor's timer under OpenSBI is a software interrupt: machine mode takes `mtimer` and writes `mip.STIP`.
- Two APLICs of one CPU with a line at the same source number are refused by `platform.devicetree()`; a device's node already names its APLIC, so a property of ours was not needed. A source set up while its line is already asking is pending at once, so a byte typed during boot is not lost. An APLIC needs a customer: nothing on the IO die interrupted the host by wire until the console did.
- **A wire takes one driver.** Write each wire output from one process of the component's own, or SystemC stops at `SC_ONE_WRITER`. A PCIe device's interrupt reaches a PLIC as a pulse, and the borrowed PLIC forgot a pulse during a claim and treated every source as edge ([upstream.md](../upstream.md#vpv-peripherals)). The NVMe function's line falls on acknowledge and rises a delta later if completions remain, so each rise is one MSI-X.
- **A level interrupt and a handler that only wakes its thread re-enter each other for ever.** The link's did; the script never showed it because a script has no handler to return from.

## The die-to-die link

- [models/d2d-link.md](../models/d2d-link.md) has the training, the timing and what it leaves out. The reset hold is 4 ms and training 1 ms, so the host's first instruction is 5 ms late; a retrain is 5.1 ms, and training a link that is already up takes 17 µs.
- **A debugger cannot write the link's registers**, so a test cannot inject a fault with `poke32`; a script on the die does it. A debugger's look crosses a link that is down; a transaction gets a bus fault with the address in `mtval`. Nothing crosses untrained, and a test of that needs an image whose first crossing is early: `hello_world` at 0.44 ms, not the disk test at 0.1 s.
- **Each die has an address map of its own, and the window between them translates.** An identity window cannot be mapped on the host, because the compute die's interrupt controller and timer sit where it would be. The walk that makes the address map and the devicetree does not clip to a window's size, so keep the IO die's main bus to what the host may reach, and a decoder (M16) has to describe itself as one memory.
- A port that two masters reach at different addresses is refused only where firmware is told the address from outside; otherwise it is a choice. A target socket takes one connection, so a flash shared by two CPUs gets a small router of its own.
- **A trace record names no sender** and tells direction only by where it was taken; its addresses are the receiving die's; the trace tests tell a command from data by size and say so. The sideband packet's layout lives twice, in C++ and in `socpuppet.ucie`, kept in step only by a decode test.
- The real link costs no measurable wall time, since DMI was saving nothing with RAM on its own die. Twenty nanoseconds a crossing is nothing to the CPU; twenty microseconds is nearly the whole run. One disk test is 4081 crossings for 69 commands.

## PCIe and NVMe

- ⚠️ **Nothing on the PCIe link says which device sent an access.** M7 told traffic apart by address; an IOMMU cannot, so the endpoint will have to mark its DMA (M15). The endpoint's capability list is MSI-X and nothing else.
- **Zephyr's PCIe code is single-controller and written for x86 and Arm**: no MSI delivery on RISC-V, nothing enables memory decoding, and the bus scan needs 3 KB of interrupt stack ([upstream.md](../upstream.md#zephyr)). Zephyr's `CONFIG_NVME_REQUEST_TIMEOUT` is not what its name says: any command waiting more than 5 ms is timed out once the 5 s timer fires, which M9's sustained writes will meet.
- **A PCIe device does nothing to its host's memory until bus mastering is on**, so an idle host is not enough for a DMA test; the SSD board's host shield exists for that.
- **A host's reset of the SSD is a handshake**: the frontend drops its queues and takes back ready, and firmware acknowledges from where it does its work, not from a handler ([models/nvme-frontend.md](../models/nvme-frontend.md)). The flash controller knows the NAND's geometry only after it is told to identify, so a read must not do anything. A refused write is a bus fault in Zephyr with the address in `mtval`.
- Every model on the NVMe path answers a debug access, and a debug write lands and starts nothing; devices on the SSD's own bus decline a debugger's write. Nothing was borrowed for the SSD: FEMU, MQSim and SimpleSSD model the whole drive from the host's side. The glue between a socket and a register block exists four times, and a review asked for one class.

## Boot ROM, flash, watchdog, system controller

- [models/rom.md](../models/rom.md), [spi-flash.md](../models/spi-flash.md), [watchdog.md](../models/watchdog.md), [system-controller.md](../models/system-controller.md) and [boot-image.md](../models/boot-image.md) say what each does and leaves out; `firmware/rom/README.md` is the ROM's program.
- **A ROM cannot tell loading from simulating by asking the kernel.** It takes debug writes until its bus master's first transaction, and GDB cannot patch it afterwards; a refused poke says why. A ROM must not be a `memory` node, or the generator gives it `zephyr,sram`. The borrowed flash is filled by a debug write through its XIP window, and its adapter refuses three things the model would do wrong ([upstream.md](../upstream.md#vpv-peripherals)).
- **Checking costs more than copying**: 23 ms of CRC to 1.5 ms of copy for 12 KiB, a byte at a time is a microsecond a byte, and OpenSBI's 2 MiB takes the ROM 4.2 s of CPU time, EDK2's 4.2 MB about nine. The ROM tier for big images runs on demand. The CRC covers the program and not the header.
- **The SDK's GCC ignores a linker script given as `-Wl,-T` in silence**; give it `-T`. The SDK's GNU linker is for bare metal and cannot make a position-independent executable (OpenSBI) or take `-z notext` (EDK2); the same SDK's LLVM links both.
- **A reset reaches the CPU and nothing else, and that was enough**, because Zephyr sets up what it uses; firmware that trusted a peripheral's reset value would be wrong here, as on many chips. A reset is a 1 µs pulse, and a busy core missed it until patched. **The quick tier does not survive a reset**: nobody puts `.data` back, so a reboot faults at address 0, or under `fw_jump` waits for a hart that never comes; a test of a reset boots from a ROM. The ROM's trap vector serves the program it jumped to until that sets its own, so firmware that traps in its first instructions gets a sentence on the console.
- Zephyr's `wdt_sifive` cannot build without an `interrupts` property, cannot switch the watchdog off, and accepts a callback it cannot call ([upstream.md](../upstream.md#zephyr)); Zephyr has `syscon` and no `syscon-reboot`, and `sys_arch_reboot` for RISC-V is an empty weak function a SoC fills; a devicetree node cannot carry a property its binding does not declare.
- `fw_jump` wants `a0` and `a1`, and nothing in Python can set a register, so the quick way to OpenSBI is QEMU's six-instruction reset vector in the ROM, and the image header gained an argument. `fw_jump` copies the devicetree to RAM plus 34 MiB and expects the next stage 2 MiB in. A 16 MiB flash did not fit a 16 MiB window ([address-map.md](../address-map.md)).

## Zephyr

- Zephyr reads one ISA name, `smcsrind`, and takes the rest as it comes. Its interrupt entry clears the `mip` bit of the interrupt it is about to handle, which a real hart ignores. Its idle thread keeps a timer armed, so `hello_world` runs to the cap, and the disk test without a drive reads an address nothing answers and waits.
- **Asking for a driver class is the application's job**: a driver that `select`s `RESET` drags the subsystem into `hello_world`. Zephyr's documented `run_custom` target does not depend on the image; the dependency is added with `cmake_language(DEFER)` ([upstream.md](../upstream.md#zephyr)).
- **ztest says each case's verdict twice**, a suite that never ran appears only in the summary as skipped, and a suite that resets its CPU starts three times; twister's console harness never reads `expect_reboot`. `CONFIG_ASSERT=y` caught an order-of-glue fault the tests did not.
- **Firmware can be mutated**: copy the module, build one image with the copy as the extra module into its own directory, and point `SOCPUPPET_FIRMWARE_DIR` at it. Firmware that cannot do its job says why on the console, and a test holds the sentence.
- Zephyr's virtio console asks for queues of one entry and blocks for the used descriptor inside a spinlock, which works on one hart because idle runs with interrupts on; its transport reads a write-only register and lays its callback table misaligned ([upstream.md](../upstream.md#zephyr)); its virtio-net takes its MAC from the devicetree and negotiates nothing; its virtiofs sample wants the label `virtio_pci` and `CONFIG_PCIE=n`; `echo_server` leaves `CONFIG_NET_L2_ETHERNET` to the board, so `firmware/build.py`'s images carry options and overlays.

## OpenSBI, EDK2 and the devicetree's dialects

- **OpenSBI reads the devicetree differently from Zephyr.** `/cpus` must have `timebase-frequency` or `sbi_timer_init` waits for ever; a CPU with no `mmu-type` is marked disabled before hand-over, so Linux sees no CPU; a mode's IMSIC is found by which CPU interrupt it names (11 or 9) and an APLIC's level by following `msi-parent`; the hart is probed, not read from the ISA list; `stdout-path` loses anything after a colon; `ssaia` is not in its extension list, `smaia` is. The generator writes the two facts, and `mmu-type` and `timebase-frequency` in both dialects.
- **The UART says it has no FIFO, so it is `ns16550` and not `ns16550a`** in both dialects; EDK2's SEC maps a UART only if it says `ns16550a`, which is a patch ([upstream.md](../upstream.md#edk2)). OpenSBI's syscon regmap compares a byte offset with a register count, so only the first quarter of a block is writable ([upstream.md](../upstream.md#opensbi)).
- **OpenSBI needs a second of CPU time**, most of it the banner through a UART on the other die. A debugger with breakpoints at the firmware's symbols is the tool for a boot that prints nothing, and the tests' GDB client is enough of one. Its payload's wait for its timer could sleep for ever if the interrupt came between the flag check and `wfi`; let the interrupt in only after `wfi`.
- **EDK2's RISC-V port**: `PFLASH0_BASE` is a `-D` on the command line, so no platform of our own; variables in RAM are a PCD; the drivers that ask for `fw_cfg` return quietly without it; SEC's temporary RAM is 32 MiB at 0x8200_0000, so 64 MiB is the least it boots with and `fw_jump`'s devicetree copy sits inside it; the firmware image in RAM is handed out as free memory; and the 64-byte section alignment stops image protection ([upstream.md](../upstream.md#edk2)). It tries Sv57, Sv48 and Sv39 and keeps the first that reads back, and maps RAM in 2 MiB pages, the one size M22 never ran.
- **The way to `Shell>` is two 5 s countdowns spent in `wfi`**; the console is a terminal, so its escape sequences are stripped before reading; `memmap` is 22 s of interpreter time, so type both commands in one boot. The boot manager boots `\EFI\BOOT\BOOTRISCV64.EFI` from a disk by itself, and with a network card tries PXE first: 65 s of simulated time waiting for DHCP. EDK2's `VirtioFsDxe` never sets its queue size, which is fine over PCI and a queue of none over MMIO ([upstream.md](../upstream.md#edk2)).
- **A boot is mostly one loop.** UEFI is 550 million instructions to the prompt, 344 million of them SEC's LZMA, and the interpreter's rate on it says more than a spike's loops ([speed-spike.md](speed-spike.md)). The EDK2 build needs libuuid's header and `iasl`, fetches every submodule, and `dtc` is on CI's Linux runner and not its Mac.

## Virtio

- [models/virtio-mmio.md](../models/virtio-mmio.md) is the transport; [virtio-spike.md](virtio-spike.md) has the catalogue and the roads to Linux. The split virtqueue is the whole of the work; `virtio-mmio` version 2 only; Zephyr negotiates `VERSION_1` and split rings, no indirect descriptors or event index.
- **Zephyr's and Linux's nodes differ**: Linux wants a bare `virtio,mmio` node, since the device says what it is in a register; Zephyr wants a child node per device, by name or by number, and the virtiofs client finds its transport by label.
- **A device must touch nothing until the doorbell write has returned**, which is the contract item the shell's mutation failed; a used chain is told by the used count, so a device may answer later from wherever its answer comes. A device's configuration is read-only unless the device takes a write: the first version let a driver change the capacity it then read back. An empty queue is never ready, a stale doorbell on a queue not set up is refused, and a looping chain is told by its length; the first test of it hung.
- **A stock `defconfig` builds the transport, blk, net, console and rng in**, NVMe as a module, 9p but not virtio-fs; and the host is already most of QEMU's `virt`, apart from the interrupt numbers. Without `SEG_MAX` Linux sends one data segment a request, slower and still correct.
- **The FUSE server translates the host's errno to Linux's by name** (macOS's `ENOTEMPTY` is 66), and nothing outside the served directory may be reachable, by `..` or by a link; three ways out were found and closed. dpkt works out an IPv4 packet's length as it packs it and not a UDP datagram's, which a mutation found; before Python says anything Zephyr sends seven IPv6 frames of neighbour discovery. One UEFI boot per device, since one platform per process: xdist runs them side by side.

## Linux

- **A stock kernel finds what three drivers did not ask for.** Python's, Zephyr's and EDK2's drivers all ran against the virtio transport, and none read `CONFIG_GENERATION`; Linux's reads it around every configuration, the read was refused, and the kernel died in `vm_generation` with a load access fault. The register was in the map and not in the model's switch. A borrowed driver finds a gap only where it looks ([models/virtio-mmio.md](../models/virtio-mmio.md)).
- **Where a kernel is when it goes quiet, the debugger says in a minute.** QBox's hart with `gdb_port=`, continue, wait for the console to stall, send the interrupt (`\x03`), read `pc`, and look it up in `linux.map`: three samples of four were in the tracing subsystem's event update, which is slow and finite, and the fourth in the next initcall. Not a hang, so a longer run, which met the fault above. The instruction trace was not needed.
- **`earlycon=sbi` is the instrument for a kernel that has not found its console.** The kernel's first words go through OpenSBI's console on the 16550, which is up before the kernel is, and they stop there once the virtio console registers: the banner is read from the one and the prompt from the other, and the kernel does not say its first words again on the second.
- **A boot is 200 s of a stock kernel's own time.** The prompt comes at 208 s of the CPU's time: the kernel's initcalls, with the tracing subsystem's event update tens of seconds among them, on a hart that counts 128 ns an instruction. On QBox's hart that is 6 s on the wall and on the interpreter 75 s, well inside the platform tests' cap, and 64 MiB of RAM was enough, as the virtio spike had asked to be checked first.
- **Through UEFI, the kernel wants room to move.** The EFI stub copies the kernel to an address it likes before it starts it, which with UEFI's own memory taken needs more than 128 MiB of RAM ("Failed to relocate kernel"), and 160 is enough. The stub says nothing on the console unless asked; the kernel's own `efi: EFI v2.7 by EDK II` is the line that shows it came through UEFI.
- **Each device meets the protocol its driver has.** Linux's `defconfig` mounts a share over 9p and not virtiofs; a second device over the same directory cost a page of C++, and the first mount passed the first time on both harts; a mount by the wrong tag, tried by hand, failed as it should (`9pnet_virtio: no channels available`). The server's review then found what the mount had not: a renamed file's fid left at its old path, a link out of the share that could not be removed, and a `chmod` through such a link that reached the file outside. A 9P server, unlike a FUSE one, must never follow the last link of a path.
- **A stand-in switches the CPU off before the kernel's last word arrives.** `poweroff` writes the system controller's register through the kernel's `syscon-poweroff` driver and the CPU stops at once, so "reboot: Power down" never reaches the virtio console's queue; the register is the fact a test can read.

## Testing method

- **A test that passes the first time has shown nothing yet.** Every such test is held by a one-line mutation of the code, and the mutations that survived earned their keep: the big-page test writing into the first 4 KiB, a watchdog told to reset that never interrupts, two real images whose length happened to be a whole number of words, a CRC held up by a leading zero, a fed stretch exactly one period long. Check a first-time pass with an image that would show the fault.
- **What reviews find that mutation cannot**: tests that can only fail by crashing, a second message on a second write of a source's mode, a bit cleared by a one-byte write. Read what exists before designing glue: the devicetree already said what a planned property duplicated.
- **Mutation gotchas**: a `.pyc` with the same mtime and size as the mutated source runs the mutation (`PYTHONDONTWRITEBYTECODE=1`), and a file moved back with its old time is not rebuilt, so touch it.
- **Zephyr's own tests find what ours do not**: fourteen suites found two bugs in borrowed models their first run. Run a new model or board under twister before trusting it ([twister.md](../twister.md)). A stand-in's deadline is the test's: the SSD's scripted host waits one simulated second to be told ready.
- **With two consoles in a test, compare times and not places, and wait for lines and not events**: the compute die runs the instant it is released, before the manager finishes saying so. Say whose line with `via=`.
- **The local run is not CI's**: no clang-tidy, no header check, no GCC on a Mac ([development.md](../development.md#before-you-push)). `lint.py --fix` formats C as well as Python, so text copied before it ran may be gone. The register maps were tested by moving every register of every block and rebuilding everything; it found the copies nobody had listed. Generated headers are excluded from clang-tidy by name, since it prefers enums to macros.
- **Twister**: `exec` must be on twister's own `PATH` or every scenario is silently built and not run; the emulator must exit 0 at its cap; `SOCPUPPET_FIRMWARE_DIR` must be in its environment since ninja runs from the build directory; a model's SCC warning lands on stdout between console lines ([twister-spike.md](twister-spike.md)). On an Intel Mac Docker's file sharing was the whole cost: a volume made it ten times faster, one invocation saved 40 percent, and ccache cost more than it saved.
- **A report that crosses a process crosses as JSON**, and JSON has no tuples: a skip's reason came back as a list from a platform test's process, and pytest's summary of skips (`-rs`) ended in a traceback until the plugin made it a tuple again. A wheel's tests run from a copy outside the source tree, so a test that reads `firmware/versions.toml` fails there and nowhere else.
- Two flakes in CI: one pytest failure inside ctest's eight jobs that was never explained, and the keyboard-interrupt test's timeout, which was coverage.py taking a lock in two Python calls ([upstream.md](../upstream.md#coveragepy)).

## Building and machines

- [development.md](../development.md) and [setup.md](../setup.md) hold the mechanics; [speed-spike.md](speed-spike.md) the measurements. The Apple silicon Air is the fastest machine at everything; the 2019 Mac Pro's process start-up makes a suite of a thousand processes three times slower; GCC 13 against 15 makes no difference.
- **The extension is built into `python/socpuppet/` by whichever tree built last**, so the Python tests run against that tree until another is built; the speed runner saves and restores it. CMake caches where it found each package, so a tree pointed at a second QBox install kept linking the first until an option changed.
- A test that hangs on a backend outlives ctest's timeout: four were found five hours later at 100 percent CPU, and `spikes/speed/run.sh` sweeps them. The wheel is about 3 MB with the CPU; cibuildwheel takes 11 to 13 minutes on Linux with ccache and 5 on macOS once cached; LLVM would add 1.5 MB and a shared library the wheel cannot assume. Debian's QEMU under `-icount shift=0` counts instructions as nanoseconds in `dmesg`, so a kernel's boot can be counted with no plugin.

## The platform and its description

- **A fidelity tier is two description functions**, and the registry has no mechanism for one ([vision.md](../vision.md)). A master that needs a different view of memory needs a router of its own; the router takes several masters with one map.
- **The registry's parameters are numbers.** A string crosses as a flag (`isa`, `modes`), a backend is the build's, and a virtio device is named by its own registry entry.
- `boards/host.py` cannot import `boards/ssd.py`, because the SSD's scripted host takes its addresses from the real host, so `Host` is generic in its drive. Driving wires from Python was never needed: Python writes to the model that owns the wire. `Platform.build()` finishes elaboration through `sc_simcontext::initialize`, which is public in the reference kernel and not in the standard.
- Python only ever runs on the kernel's main stack, and a model's exception is parked and re-raised from `run()` ([architecture.md](../architecture.md#how-python-gets-called-from-inside-the-simulation)).
